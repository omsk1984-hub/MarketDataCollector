## 9. Главные выводы

1. **~18K ticks/sec** — пропускная способность выросла на 80% за счёт увеличения batch_size до 2000
2. **~6.6% дубликатов** — увеличилось вдвое, вероятно, из-за большего батча (больше перекрытий между каналами)
3. **Batch = 2000** — среднее время записи ~105 мс, что даёт ~19,000 ticks/sec по записи
4. **Высокая аллокация (~150 MB/сек)** — требует оптимизации (pooling,减少 alloc)
5. **Timer count = 31,274** — аномалия, возможная утечка таймеров
6. **Lock contention ~76/сек** — будет узким местом при дальнейшем росте
7. **Один выброс 3.96 сек** — вероятно, совпал с GC Gen2 (4 GC за 15 сек)

### Рекомендации

1. Уменьшить batch_size до 1000-1500 для снижения дубликатов и латентности
2. Оптимизировать аллокации (object pooling, сократить string allocations)
3. Исследовать причину 31K таймеров (искать неутилизированные Timer/Task.Delay/CancellationTokenSource)
4. Оптимизировать lock contention (пересмотреть блокировки в дедупликации/агрегации)
5. Рассмотреть `ConcurrentDictionary` или stripe locking для снижения конкуренции
