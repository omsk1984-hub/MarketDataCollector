## 8. Вывод по P2 (contention/CTC) — требуется `contention-cpu`

- TopN `gc-verbose` показывает CTC ≈53% exclusive, но профиль **gc-verbose** для CTC ненадёжен:
  1. Сам EventPipe-инструментарий активно создаёт `CancellationTokenSource`;
  2. `EventPipeMetadataGenerator` (6.79%) в топе — маркер затрат инструментации;
  3. В hot path при непустом канале `linkedCts` не создаётся (только в flush-ветке при пустом канале; в этом прогоне `fills: 0%` — канал почти всегда непуст, значит flush-путь почти не срабатывал).
- **Изменений прод-кода по P2 не выполнено** (по плану B1 → B2 только при подтверждении real hot path).
- Для подтверждения требуется прогон `start_loadtest.ps1 -TraceProfile contention-cpu` (по правилам — с явного согласия на нагрузочный тест).

## 10. Ключевые выводы и рекомендации (по приоритету)

1. ✅ **[P1 — частично устранено] A1 подтверждён**: batch 5000 дал avg −19%, max −18%, write throughput +37%. Дропов по-прежнему 0 (6-й прогон). **Рекомендуется оставить batch=5000.**
2. ⚠️ **[P1 — остаток] Накладная вокруг INSERT** (~760 мс avg против ≤432 мс чистого insert) — конкуренция writer+metrics-экспорта в общем pool, span'ы `ProcessBatch`. **Меры:** выделить писателя в отдельный ThreadPoolExecutor; рассмотреть снижение `ProcessBatchTraceSampling` (10→100) и полный вынос OTLP-экспорта из writer-потока. Это следующая точка ускорения, а не SQL.
3. ⚠️ **[P2] Contention остаётся ~+2.1K**, CTC в топе `gc-verbose` — **требуется прогон `contention-cpu`** для отделения real hot path от артефакта инструментации. Без него изменения прод-кода по P2 неоправданны.
4. ✅ **[P3] LOH 24.2 MB** — слегка вырос из-за батчей 5000, но вблизи базы (17 MB); `Decimal`-конструктор 2.2% (минимум за историю). Контроль продолжать.
5. **[P5]** Логи A2 работают корректно — `tail` помечает только настоящие хвосты insert (>1 с), в этом прогоне их нет.
