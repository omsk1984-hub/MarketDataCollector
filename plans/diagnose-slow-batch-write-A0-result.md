# A0 — Результат диагностики узкого места записи батчей (P1)

**Дата:** 13.09.2026 · источник прогона `counters_20260913_021227.csv` + прямой `EXPLAIN` в `marketdata-postgres`.

## Метод и важное замечание об инвазивности

В ходе A0 использовался `EXPLAIN (ANALYZE)` с реальным INSERT. Первые два запуска **выполнены без обёртки `BEGIN/ROLLBACK` и модифицировали прод-таблицу** (+2500 diag +2500 binance строк). Это ошибка диагностики. **Данные восстановлены полностью**:
- `DELETE exchange='diag'` (−2500),
- `DELETE WHERE timestamp<'1970-01-12' AND receivedat>'2026-09-12 23:15:00+00'` (−2500 binance-диагностических).
- Финальный контроль: `count(*) = 1 648 981` — строго равно исходному прогону. ✅

> **Урок для следующих прогонов:** любые `INSERT`/`EXPLAIN ANALYZE` оборачивать в `BEGIN; ...; ROLLBACK;` и использовать уникальный маркер (`exchange='a0diag'`), который можно надёжно отфильтровать.

## Результаты диагностики

### 1. Схема (A0-1)
| Параметр | Факт |
|---|---|
| Таблица | `rawticks` — **native partitioned by `timestamp`** |
| Дочерние day-партиции | `rawticks_2026_09_12 ... _09_18` — **пустые (16 kB)** |
| Куда ушли данные прогона | **ВСЕ 1 648 981 в `rawticks_default`** (348 MB) |
| Причина | timestamp данных — **эпоха `1970-01-11 20:59:59`–`21:27:28 UTC`** (FakeTickServer берёт фиксированный base, а не текущее время) → не попадает ни в одну 2026-day-партицию → всё в default |
| PRIMARY KEY | `(id, timestamp)` |
| UNIQUE index | `IX_rawticks_ticker_exchange_timestamp (ticker, exchange, timestamp)` **без partition key** |

> ⚠️ **Партиционирование фактически не работает** для тестовых данных: вся нагрузка (и батчи, и уникальные-индексы) упирается в одну растущую `rawticks_default`. Это делает и без того «неидеальный» конфликтный индекс ещё дороже (одна большая таблица вместо дня-партиций).

### 2. Серверный план INSERT (A0-2) — `EXPLAIN (ANALYZE, VERBOSE, BUFFERS)`
Чистый INSERT 2500 **уникальных** строк в `rawticks_default` (1.65M строк):

| Метрика | Значение |
|---|---|
| Execution Time | **48.4 мс** (повтор с binance — 35.5 мс) |
| Tuples Inserted | 2500 |
| Conflict Arbiter Indexes | `IX_rawticks_ticker_exchange_timestamp` |
| Conflicting Tuples | 0 |
| Buffers | shared hit=27325 (всё в кэше) |

**Вывод: сервер на чистой вставке уникальных ключей быстр (~35–48 мс).** H2 (планировщик/индексы как причина 949 мс) — **опровергнута** для нулевых конфликтов.

### 3. Распределение batch_duration по времени (A0-3)
Из `ticks_batch_write_duration_milliseconds_sum` по сэмплам (значение — длительность **отдельного батча**, т.к. `batch_size=2500`, но `inserted_count` у каждой строки свой):

| Сэмпл | min (мс) | max (мс) | Примечание |
|---|---|---|---|
| 23:12:30 | 63 | 674 | старт |
| 23:12:35 | 67 | 1065 | |
| 23:12:40 | 67 | 1246 | |
| 23:12:45 | **42** | **1690** | максимум растёт |
| 23:12:50 | 118 | **1846** | пик нагрузки |
| 23:14:16 | **46** | 1397 | финал (после нагрузки) |

- **Батчи вовсе не «ровные».** В одном сэмпле разброс 42 мс ↔ 1846 мс.
- Минимумы (42, 46, 63, 67 мс) **совпадают с серверным EXPLAIN (35–48 мс)** → когда нет помех, INSERT быстр.
- **Хвосты (1.2–1.8 с) нарастают к пику нагрузки и частично спадают после её окончания.** Это согласуется с **растущей стоимостью записи при активной конкуренции и росте таблицы/индекса**, а не со стабильно-медленным сервером.

### 4. Корреляция с GC (A0-4)
- `gc_duration_nanoseconds_total` финал = **117.18 мс** за весь прогон (~120 c).
- `gc_allocations` = +1 281 MB (~18.6 MB/с).
- **GC-паузы суммарно мизерно** (117 мс) — они **не могут** породить одиночные хвосты 1.3–1.8 с. H4 (GC как причина замедления) — **опровергнута**. Аллокации высоки, но не тормозят запись паузами.

## Итоговый вывод A0

| Гипотеза | Вердикт |
|---|---|
| H2 сервер/индексы/план | ❌ не причина (48 мс на уникальных) |
| H4 GC-паузы | ❌ не причина (117 мс суммарно) |
| H1 конфликтный индекс без partition key | ⚠️ усугубляет (вся нагрузка в одной default-партиции), но на чистой вставке быстр |
| H3 клиент/Npgsql/конкурентность + хвосты | ✅ **наиболее вероятна** |

**Корень:** серверный INSERT быстр; медленные батчи — **хвосты, возникающие на пике нагрузки** из-за:
1. **Одной растущей `rawticks_default`** вместо day-партиций (партиционирование обойдено из-за timestamp-эпохи у FakeTickServer) — все уникальные-индексные проверки и вставки идут в одну большую таблицу.
2. **Конкурентной записи батчей и клиентской накладной** (Npgsql-кодирование `numeric[]`, command round-trip, возможные блокировки на индексе при малопараллельной высокой вставке).
3. Рост хвостов вместе с объёмом указывает на **цену поддержания уникальности в растущем индексе** при высокой скорости.

### 5. Подтверждение корня на уровне генератора (A0-5)
Источник: `tests/FakeTickServer/TickGeneratorService.cs`:
- `timestamp` в JSON = `tradeId` (строго монотонный long), а не текущее время;
- `tradeId` стартует от `random.NextInt64(100_000_000, 1_000_000_000)` (строка 111) ≈ **1e8–1e9**;
- Unix-секунды 1e8 = ~11.6 суток после эпохи → **`1970-01-11`** — то самое значение в БД.

⚠️ **Вывод:** текущий `start_loadtest` генерирует тики со «сломанным» временем (эпоха + ~11 дней). Это:
1. Оправдовывает весь уход данных в `rawticks_default`;
2. Делает партиционирование по `timestamp` бесполезным в этом тесте;
3. Искажает любые тесты, зависящие от времени (TTL, retention, партиции).

Соответственно, A0 завершён: **первопричина медленных батчей в данном прогоне — не сервер, а сочетание «вся нагрузка в одну default-партицию (из-за эпохи timestamp)» + клиентские хвосты под пиком.** После исправления генератора (реальный `timestamp`) можно пере-прогнать и переоценить P1 заново.

## Рекомендации (обновляют основной план устранения)

**Приоритет сдвигается с A.1/A.2 в сторону схемы и клиентской конкурентности:**

1. **[P0] Починить партиционирование для тестовых данных** — FakeTickServer должен выдавать актуальный `timestamp` (близкий к `now()`), тогда данные лягут в day-партиции, а `rawticks_default` перестанет расти на 1.6M строк. Это разгрузит конфликтный индекс и вставку.
   - Либо добавить в `PartitionMaintenanceService` отдельную партицию для данного диапазона теста.
   - Это **самая дешёвая и вероятно устраняющая** мера.
2. **[P1] Клиентская накладная Npgsql/конкурентность** — проверить: один writer пишет последовательно, но параллельно с ним работают metrics-export и 3 WS-клиента на том же пуле. Оценить перевод записи в **отдельный выделенный thread-pool/поток** или увеличение `batchSize` (сейчас 2500; сервер показывает ~48 мс на 2500 → можно 5000–10000 с тем же round-trip оверлхедом, удвоив пропускную).
3. **[P2] Логирование хвостов** (A.4 из прошлого плана) — критично: сейчас батчи 1.8 с не логируются, что слепит операцию.
4. **A.1/A.2 (серверный каст/буферы numeric, ToString)** — **снижены в приоритете** до соответствующего: сервер и так быстр, а цены на строки второстепенны относительно схемы/конкурентности.

## Аномалия сбора (добавление)
Дополнительно: **`receivedat`** — весь прогон имеет `receivedat` из диапазона `2026-09-12 23:12:22–23:14:24`, а `timestamp` — эпоха 1970. Это подтверждает: воркер проставлял `receivedat=now()`, а `timestamp` брал из данных биржи (эпоха). Нормальная картина — `timestamp` данных близок к `now()`, расхождение на ~58 лет было бы видно и в проде. **Проверить FakeTickServer/TickGeneratorService** — укоротить timestamp-эпоху до текущей даты.
