## Этап 3.2 — Пул Npgsql-буферов / переиспользование `byte[]` (основное решение)

**Цель:** сократить LOH-фрагментацию (сейчас 8.58 MB, 18%) и частоту повторных больших `byte[]`-аллокаций.

**Место:** [`BulkInsertFastAsync`](src/MarketDataCollector.Infrastructure/Repositories/RawTickRepository.cs:446), вызывает `_context.Database.ExecuteSqlRawAsync(SqlTickDataBulkCopy, _tickDataParameters, ...)`.

**Текущее состояние:** пред-созданы массивы параметров (`ReusableArrayCache` + `NpgsqlParameter[]`), но сама сериализация значений параметров в бинарный протокол Npgsql выполняется каждый раз заново → большие `byte[]` в LOH.

**Кандидаты (выбор по риску/эффекту):**

| Подход | Описание | Риск |
|---|---|---|
| A. Npgsql binary COPY (`BeginBinaryImport`) | Вместо UNNEST+`ExecuteSqlRawAsync` — нативный bulk-импорт; Npgsql пишет бинарный COPY в сетевой поток, не создавая больших `byte[]`. Убирает LOH-источник и запрос целиком. | Средний (смена механизма записи, нужно сохранить `ON CONFLICT DO NOTHING`, дедупликацию PK и `id` generation). |
| B. Переиспользование `byte[]`-буферов сериализации | Обернуть сериализацию (кастомный конвертер / пул `ArrayPool<byte>`) — целевая заточка, но глубже лезет во внутренности Npgsql и хрупко к апгрейдам. | Высокий (внутренности Npgsql). |
| C. Разбиение сериализации на буферы <85 KB | Снизить размер крупных `byte[]` до < порога LOH. | Средний (переработка формата параметров). |

**Рекомендация:** изначально приоритет — **A (BeginBinaryImport)**, но после бинарного разбора (3.1) выяснилось, что он решает только **вторичный** источник (`byte[]` ~5.2 MB + transient-фрагментация), не трогая доминирующий резидентный `TickData[]` канала. При этом требует `CREATE TEMP TABLE` + COPY + `INSERT ... SELECT ... ON CONFLICT` (DDL на батч) — риск для стабильности (дропы 0, запись 97%).

**Решение (2026-08-05): Подход A отложен.** Возврат к нему — только если прогон 3.4 покажет, что компактинг по порогу не снизил фрагментацию достаточно, и выгода от устранения `byte[]` перевесит риск DDL.

## Этап 3.3 — LOH-компактинг по порогу фрагментации ✅ (реализовано)

**Было (нарушало рекомендацию):** [`Program.cs:22-38`](src/MarketDataCollector.Workers/MarketDataCollector.Worker/Program.cs:22) — безусловный `CompactOnce` каждые 5 минут.

**Стало:** [`Program.cs:22-55`](src/MarketDataCollector.Workers/MarketDataCollector.Worker/Program.cs:22) — фоновый таск проверяет каждые 5 минут фрагментацию через `GC.GetGCMemoryInfo()` (`FragmentedBytes` / `HeapSizeBytes`) и применяет `CompactOnce` **только** при доле фрагментации > 15% (сейчас ~18% → порог пройден).

**Уточнение по API .NET 8:** у `GCGenerationInfo` нет `FragmentedAfterBytes` (компилятор CS1061). Использован агрегат `GCMemoryInfo.FragmentedBytes`/`HeapSizeBytes` (доступен с .NET 5) — LOH вносит основной постоянный вклад в фрагментацию heap. Порог вынесен в константу `LohCompactionFragmentationThreshold = 0.15`.

**Сборка:** `Build succeeded, 0 errors, 0 warnings`.
